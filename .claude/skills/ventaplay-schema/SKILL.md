# VentaPlay Database Schema Reference

## Description

**Trigger this skill when:** Working on database queries, Supabase client calls, migrations, RLS policies, Edge Functions, or any task that requires knowledge of table structures, column types, foreign key relationships, or constraints.

This skill provides a complete map of the VentaPlay PostgreSQL schema (Supabase). All 193 tables in the `public` schema are organized into 20 functional domains with full column details, FK relationships, and constraints in the `references/` files.

## Quick Reference

- **193 tables** in `public` schema
- **~305 FK relationships**
- **Multi-tenant**: Most tables have `organizacion_id` → `organizaciones.id`
- **IDs**: UUID with `gen_random_uuid()` default
- **Timestamps**: `created_at`/`updated_at` with `now()` default
- **Supabase config**: `max_rows = 1000` — never rely on `.range(0, 9999)` for "all" rows

## Key Entity Relationship Chains

### CRM Core
```
contactos (1:1)→ clientes (1:N)→ cliente_tag_asociaciones (N:1)→ cliente_tags
                  clientes (N:M)→ cliente_empresa (N:M)→ empresas
                  clientes (1:N)→ cliente_interacciones
                  contactos (1:N)→ contacto_mensajes
```

### Appointments
```
citas → contactos (via contacto_id)
citas → servicios (via servicio_id)
citas → profesionales (via profesional_id)
citas → sucursales (via sucursal_id)
citas → organizaciones (via organizacion_id)
agenda_disponibilidad → profesionales + servicios + organizaciones
```

### Atenciones (Service Sessions)
```
atenciones → contactos + servicios + profesionales + organizaciones
atenciones (1:N)→ atencion_platos (1:N)→ atencion_plato_componentes
atenciones (1:N)→ atenciones_logs
ingreso_atenciones → atenciones + ingresos
```

### Payments
```
ingresos → organizaciones + contactos + medios_pago
link_pagos → organizaciones
ventas_externas (1:N)→ ventas_externas_items → productos_stock | platos (líneas de plato en autopago kiosko)
ventas_externas → ventas_externas_boletas_electronicas
atenciones → atenciones_boletas_electronicas | atenciones_boletas_honorarios (split de comisión por profesional, DTE 80)
atenciones → ventas_externas (venta_externa_origen_id, kiosko) | cotizaciones (cotizacion_origen_id, conversión)
egresos → organizaciones + usuarios + sucursales (no atencion / no medio_pago FK; medio_pago is enum)
egresos (self-FK)→ egresos.id (egreso_original_id, for tipo='reverso_egreso')
```

### Subscriptions
```
suscripciones → clientes_suscripcion + plataformas_suscripcion + organizaciones
pagos_suscripcion → suscripciones
configuracion_suscripcion → organizaciones
```

### Funnels & Opportunities
```
funnels (1:N)→ estados_funnel
oportunidades → funnels + estados_funnel + contactos + organizaciones
oportunidades (1:N)→ historial_oportunidades
oportunidades (1:N)→ actividades_oportunidad
oportunidades (N:M via oportunidad_tag_asociaciones)→ oportunidad_tags
```

### Services & Professionals
```
servicios (N:1)→ servicio_categorias (FK servicios.categoria_id, ON DELETE SET NULL)
servicios (N:M via servicio_profesional)→ profesionales
servicios (N:M via servicio_tags/servicio_tag_asociaciones)→ tags
servicios (N:M via producto_servicio)→ productos
profesionales → usuarios (via usuario_profesionales)
profesionales → categorias_profesionales
```

### Flows & Automations
```
flujos_configuracion (1:N)→ flujos_ejecuciones (1:N)→ flujos_pasos_ejecucion
automatizaciones_ejecuciones (standalone, tracks automation runs)
```

### Multi-Tenant Pattern
```
organizaciones ←── (organizacion_id FK on ~90% of tables)
organizaciones (1:N)→ sucursales
organizaciones (1:1)→ organizaciones_facturacion
usuarios (N:M via user_roles)→ roles (1:N)→ role_permissions → permissions
```

## How to Use

1. **Find which domain a table belongs to**: Check the Domain Map above
2. **Get full column details**: Read the corresponding `references/*.md` file
3. **Understand relationships**: Check the FK chains above or `references/relationships.md`
4. **Build Supabase queries**: Use FK names for `.select()` joins — FK constraint names follow pattern `tablename_columnname_fkey`

### Supabase Query Patterns

```typescript
// Basic nested select following FKs
const { data } = await supabase
  .from('contactos')
  .select('*, clientes(*)')

// INNER JOIN filtering with renamed embed (avoids fetching all rows)
const { data } = await supabase
  .from('contactos')
  .select('*, clientes!clientes_contacto_id_fkey!inner(*, filter_tags:cliente_tag_asociaciones!inner(tag_id))')
  .in('clientes.filter_tags.tag_id', selectedTagIds)

// Never use .in() with large UUID arrays — PostgREST serializes in URL
// Instead use !inner joins or RPC functions
```

### Recent changes (2026-07-27 — push notifications para la app móvil: NUEVA TABLA `device_push_tokens`)

Una migración (`20261106120000_device_push_tokens.sql`) — **1 tabla nueva (192 → 193)**: `device_push_tokens` (Tasks & Misc 16 → 17). Aditiva; no toca ninguna tabla existente (el trigger nuevo vive en `notificaciones` pero no altera su schema).

- **NUEVA TABLA `device_push_tokens`** — lado servidor de las push notifications de la **app móvil** (repo Expo aparte, que ya tenía el cliente listo). Un token de Expo por dispositivo, colgado de **`usuario_id`** (la sesión que se logueó en ese teléfono), **NO** de `profesional_id`: `notificaciones.profesional_id` es el destinatario, así que el envío resuelve `profesional_id → usuario_profesionales → usuario_id[] → device_push_tokens`. Colgarlo del profesional se rompe con admin/manager (sin fila de profesional) y con un usuario vinculado a varios profesionales. `expo_push_token` es **UNIQUE** — eso hace que re-loguearse en el mismo teléfono con otra cuenta sea un `upsert ... on conflict` en vez de dos filas mandándole el push a la persona equivocada. Sin `organizacion_id` (se deriva de `usuarios`; sin RLS no compra aislamiento). **Sin RLS — grants-only** (anon/authenticated/service_role). **Sin retención/cron**: un ticket `DeviceNotRegistered` (app desinstalada) hace que `send-push` borre la fila, y borrar el usuario cascadea. See [tasks-misc.md](references/tasks-misc.md#device_push_tokens).

- **Trigger `trg_notificar_push` ON `notificaciones`** (misma migración) — **AFTER INSERT** → `notificar_push_to_edge()` (SECURITY DEFINER, `search_path = ''`) hace `net.http_post` a `<supabase_functions_url>/send-push` con `to_jsonb(NEW)`, timeout 2000 ms, envuelto en `EXCEPTION WHEN OTHERS → RAISE WARNING` para no abortar jamás la transacción que creó la cita. Mismo patrón que `trigger_oportunidad_cambio_estado_to_edge` (`20260711120000`). **Solo INSERT** — marcar `has_been_seen` es un UPDATE y no debe re-notificar. Como `notificaciones` ya se llena por triggers de BD sobre `citas`/`atenciones`/`consumo_ayudantes`, el push cubre todo origen (frontend, edge functions, RPCs, MCP) sin tocar ningún caller, y hereda el dedup de 10s por `(cita_id, profesional_id, tipo)` de `_insert_notificacion`. ⚠️ Requiere `app_global_config.supabase_functions_url` seteado en el ambiente — sin eso es un no-op silencioso.

- **Edge function `send-push`** (`supabase/functions/send-push/index.ts`, `verify_jwt = false` en `config.toml` — pg_net manda la anon key, no un JWT de usuario). Chunks de 100 (límite de Expo), `channelId: 'default'` (debe coincidir con el `ANDROID_CHANNEL_ID` de la app), título derivado de `tipo` (`origen` solo refina `asignada`: derivación vs ayudante), `data: {notificacionId, citaId, atencionId, consumoId}` para el deep-link. Secret opcional `EXPO_ACCESS_TOKEN`. Poda tokens con `details.error === 'DeviceNotRegistered'`.

### Recent changes (2026-05-26 — Criterio sucursal en Campañas v3, PR #897)

Extiende el modelo de targeting v3 de Campañas con **dos formas complementarias** de filtrar por sucursal: (1) criterio independiente `categoria='sucursal'` que combina via Y/O con tag/funnel/fecha; (2) sucursal opcional embebida en el `valor_jsonb` del criterio `fecha_atencion` para consultas tipo "última visita a sucursal X en rango Y". - **`campanas_criterios.categoria` CHECK extendido** (migration `20260614120000_campanas_criterio_sucursal.sql`) — agrega `'sucursal'` a la lista: `CHECK (categoria IN ('tag','funnel','fecha_atencion','sucursal'))`. El CHECK `valor_check` también se actualiza: `sucursal` se une a `tag`/`funnel` en la rama referencial (`valor_id NOT NULL AND valor_jsonb NULL`). Compatible 100% con campañas existentes — el constraint sigue aceptando las 3 categorías originales sin cambios. `valor_id` para `categoria='sucursal'` apunta a `sucursales.id` (sin FK real — patrón polimórfico igual que tag/funnel). - **`campanas_criterios.valor_jsonb` shape extendido para `fecha_atencion`** (misma migration) — el objeto ahora soporta `sucursal_id?: uuid | null` opcional: `{desde, hasta, modo, sucursal_id?}`. Cuando `sucursal_id` está set, el filtro de fecha se restringe a atenciones en esa sucursal (resolución histórica). Cuando es `null`/`undefined` (campañas pre-feature), considera todas las sucursales — retrocompat total. La defensa `criteriosBdToInput.normalizarFechaJsonb` setea `sucursal_id: v.sucursal_id ?? null` al leer de BD, normalizando campañas pre-feature.

- **RPC `get_clientes_por_sucursal(p_org_id uuid, p_sucursal_id uuid) → table(cliente_id uuid)`** (misma migration) — nueva RPC dedicada al criterio independiente `categoria='sucursal'`. Trae clientes con ≥1 atención efectiva (`estado IN ('finalizada','en_curso','reabierto')`) en la sucursal indicada, vía `COALESCE(citas.sucursal_id, profesionales.sucursal_id)`. SECURITY DEFINER, STABLE, search_path public. Validation: ambos parámetros NOT NULL con RAISE EXCEPTION explícito. Granted to authenticated, anon, service_role. Canonical callers: `useCampanaTargetPreview.resolverCriterio` (frontend), `prepare-campana-send/index.ts` (Phase 1), `send-campana-whatsapp/targeting-service.ts` (legacy WhatsApp programadas).

Cuando `NULL` (default), comportamiento idéntico al previo (sin filtro de sucursal) — **garantiza retrocompat 100% con campañas existentes**. Cuando set, filtra por sucursal resuelta vía COALESCE: en modo `'cualquiera'` agrega cláusula `AND COALESCE(c.sucursal_id, pr.sucursal_id) = p_sucursal_id`; en modo `'ultima'` usa un CTE `atenciones_en_sucursal` para computar la última visita **por (cliente, sucursal específica)**, no la global (un cliente cuya última visita global fue en otra sucursal pero su última visita a X cae en rango sí entra). DROP + CREATE en transacción atómica con `NOTIFY pgrst, 'reload schema'` al final.

- **Validación de huérfanos extendida en `CampanaFormModal`** — la detección de criterios huérfanos (chip rojo + AlertTriangle en el builder + submit bloqueado) ahora cubre: (1) criterio `categoria='sucursal'` con `valor_id` apuntando a sucursal eliminada; (2) criterio `categoria='fecha_atencion'` con `valor_jsonb.sucursal_id` apuntando a sucursal eliminada. ### Recent changes (2026-05-22 → 2026-05-24 — payment-state hardening + feriado exclusions + sesiones diagnostic)

Six migrations applied in the window between the ventana_minutos rollout and the Google Meet integration. Two are **critical production bug fixes** (real duplicate-charge incidents in customer orgs), one adds a schema column, and three are RPC consolidations/refactors. None destructive.

- **`ingreso_cuenta_como_pago(uuid)` predicate + cascading rewrites** (migration `20260607120000_fix_calcular_estado_pago_reverso_pos_failed.sql`) — **CRITICAL fix for duplicate-charge bug**. The payment-completeness formula was duplicated across 4 implementations (1 SQL + 3 TS), and all of them subtracted EVERY reverso unconditionally without checking the original ingreso's state. When a POS ingreso in `pos_status IN ('pending','failed','cancelled','timeout')` was anulado, the reverso still subtracted from the atención's `estado_pago` — but the original never contributed positively (the function already excluded it) → **double penalty** → atención stuck at `por_pagar` → cashier saw "por pagar" and charged again → real duplicate charge. **Customer impact**: Club La Barba, atención `a7b165bb` (Mane Argomedo), 13-may-2026. **Fix**: new canonical predicate `ingreso_cuenta_como_pago(uuid)` defines what counts as a positive payment; reversos only subtract if the original ingreso counts. Conservation guaranteed: `original=+X ⇔ reverso=-X`. Rewrites `calcular_total_pagado_atencion` (the numeric core) and `calcular_estado_pago_atencion` (the state-resolver, used by 3 triggers) on top of the predicate. **Two new RPCs**: `obtener_resumen_pago_atencion(uuid)` returns the full breakdown (total_ingresos, total_reversos, total_neto, total_giftcards, total_canjes, cantidad_ingresos, cantidad_reversos, ultimo_pago, tiene_reversos, saldo_pendiente, estado_pago) for the frontend — replaces the TS-side calculation in `useIngresosPorAtencion` + `packPaymentHelpers`. `recalcular_estado_pago_atencion(uuid)` calculates AND persists (idempotent — only UPDATEs when state changes) — replaces ~130 lines of TS in `IngresosService.actualizarEstadoPagoAtencion`. Functions still bear `SECURITY DEFINER` and grants stay broad (anon/authenticated/service_role) — consistent with dev posture. See [atenciones-sessions.md](references/atenciones-sessions.md) + [payments-billing.md](references/payments-billing.md).

- **`actualizar_estado_pago_trigger()` rewrite** (migration `20260609120000_fix_trigger_estado_pago_pos_status_race.sql`) — **CRITICAL fix #2 — also a real duplicate-charge incident**. The trigger `trigger_actualizar_estado_pago_ingresos` on `ingresos` had an early-return check that only watched `monto`, `tipo`, `motivo_anulacion`. When the async POS cron (`cron-check-pending-payments` / `check-pos-payment`) flipped `pos_status='pending' → 'completed'` minutes after the INSERT, the trigger hit the early-return → `atenciones.estado_pago` stayed stale at `por_pagar` → operator saw "por pagar" on the calendar and charged again → **real duplicate charge**. **Customer impact**: Tonos, 15-may-2026, Lorena Sierra, $76.980 over-charged. **Additionally**, the function didn't handle multi-payment: when `ingresos.atencion_id IS NULL` AND `es_pago_multiple = true` (a payment that distributes across N atenciones via the `ingreso_atenciones` junction), it couldn't find an atención and recalculated nothing. **Fix**: added `pos_status` to the early-return predicate (trigger now SI reacts to `pending → completed` transitions) + added a multi-payment handler that iterates `ingreso_atenciones` and recalculates each atención on the bridge, with per-iteration BEGIN/EXCEPTION so one failure doesn't abort the others.
